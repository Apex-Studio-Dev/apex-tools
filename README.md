# apex-tools

**apex-tools** is a custom Android SDK manager plus repackaged Android SDK components for **aarch64 (arm64)** and **armv7 (arm)** hosts.

Google's official `cmdline-tools` / `sdkmanager` and the SDK components they ship are **x86_64-only**. apex-tools solves this by:

1. Building each SDK component (platforms, build-tools, platform-tools, CMake, NDK) natively for ARM hosts in CI.
2. Publishing them as GitHub Releases, indexed by a machine-readable `catalog.json`.
3. Shipping **`apex`**, a small Go CLI that runs natively on arm64/arm and installs those packages into a standard Android SDK layout — Gradle, CMake, and NDK tooling work against it unchanged.

## Packages

| Package            | Versions                | Built from                        |
|--------------------|------------------------------------------------------|-----------------------------------|
| `platforms`        | android-30 … android-37.2 (ints 30–37)               | AOSP source (`builder/android-sdk-custom`) |
| `build-tools`      | 33.0.0 … 37.0.0                                      | AOSP source (`builder/android-sdk-custom`) |
| `platform-tools`   | 37.0.1                                               | AOSP source (`builder/android-sdk-custom`) |
| `cmake`            | 3.18.1 … 4.1.2                                       | Upstream CMake (`builder/cmake-custom`) |
| `ndk`              | r26.0 … r30.0 (all letter revisions)                 | Official NDK skeleton + rebuilt toolchain (`builder/android-ndk-custom`) |

Host tags: `linux-arm64`, `linux-arm` (a `linux-x64` convenience variant may also be published).

Versioning of each package mirrors the official Google `Pkg.Revision` (e.g. NDK r27d → `27.3.13750724`), so tools that parse `source.properties` behave as with the official SDK.

## Catalog

`catalog.json` is regenerated by CI from the repo's release assets and pushed to the `catalog` branch (file at branch root). It is served raw at:

```
https://raw.githubusercontent.com/Apex-Studio-Dev/apex-tools/catalog/catalog.json
```

Entries carry: package path (`build-tools;33.0.0`), version, supported hosts, download URL, byte size, and SHA-256. Override the URL with `APEX_CATALOG_URL` (useful for mirrors/private forks).

## CLI (`apex`)

Install the binary for your host from the [latest CLI release](https://github.com/Apex-Studio-Dev/apex-tools/releases/latest) (`apex-linux-arm64` / `apex-linux-arm` / `apex-linux-amd64`), e.g.:

```
curl -fsSL -o $PREFIX/bin/apex https://github.com/Apex-Studio-Dev/apex-tools/releases/latest/download/apex-linux-arm64
chmod +x $PREFIX/bin/apex
```

Usage:

```
apex --list [--all|--json]          list available/installed packages
apex install <pkg>... [--force]     install (e.g. "platforms;android-34" "build-tools;37.0.0")
                                    - already-installed package: prompts to replace (TTY),
                                      skips with a hint otherwise; --force overwrites
apex uninstall <pkg>...             remove installed packages
apex update                         upgrade installed packages side-by-side
apex licenses [--accept]            show/accept license (writes licenses/ for Gradle)
apex --version                      print CLI version
```

Environment:

| Variable            | Meaning                                        |
|---------------------|------------------------------------------------|
| `ANDROID_HOME`      | SDK root (fallback: `ANDROID_SDK_ROOT`) — required |
| `APEX_CATALOG_URL`  | catalog.json URL override                      |

Install layout mirrors the official SDK (`$ANDROID_HOME/<component>/<version>`), with `package.xml` and `source.properties` generated per package so Android tooling (Gradle, AGP, cmake, ndk-build) recognizes the install. Extraction is checksum-verified (SHA-256 from the catalog), atomic (temp dir + rename), and zip-slip protected. Downloads/extracts show realtime progress.

> Termux note: releases built on stock Linux read `/etc/resolv.conf`; on Android that path usually does not exist and Go falls back to `[::1]:53` (no DNS). The locally-built Termux Go reads `$PREFIX/etc/resolv.conf`, so on-device builds work best — or build the CLI in Termux (`pkg install golang && go build -o $PREFIX/bin/apex ./cmd/apex`).

## Repository layout

```
cmd/apex/            Go CLI source (list/install/uninstall/update/licenses)
scripts/
  build-cli.sh       cross-build apex (linux-arm64 / arm / amd64)
  gen-catalog.sh     regenerate catalog.json from GitHub release assets
  make-package.sh    add package.xml/source.properties to a component tree
  split-sdk.sh       split official SDK component trees into per-version packages
builder/
  android-sdk-custom/  build platforms, build-tools, platform-tools from AOSP
  android-ndk-custom/  build NDK toolchains from official NDK skeletons + llvm-custom
  cmake-custom/        build CMake with Android cross-target support
patches/ …            per-component patches (bionic fixes, shebangs, …)
.github/workflows/
  cli.yml             test + build apex; release on `v*` tags
  build-sdk.yml       one platforms/build-tools/platform-tools version per dispatch
  build-cmake.yml     one CMake version per dispatch
  build-ndk.yml       one NDK revision per dispatch
  catalog.yml         regenerate + push catalog.json to the catalog branch
  builder-images.yml  builder container images (ghcr.io)
licenses/apex-sdk-license   SDK redistribution notice shipped into packages
```

## Building components

Every component build runs in its builder container (see `builder-images.yml`), one version per workflow dispatch, for both `linux-arm64` and `linux-arm` matrices. Packages are produced by `make-package.sh` and attached to a release named `apex-<pkg>-<version>`.

To build locally inside the corresponding builder image:

```
docker run --rm -v "$PWD:/work" -w /work/builder/cmake-custom \
  -e PLATFORM=bionic -e TARGET=aarch64-linux-android \
  ghcr.io/apex-studio-dev/cmake-builder:latest bash -c 'scripts/build.sh'
```

(Each `builder/*/scripts/build.sh` documents its env knobs — `PLATFORM`, `TARGET`, version, and for NDK: `LLVM_TAG`/`LLVM_REV` pointing at an llvm-custom release.)

## Contributing / development workflow

- CLI changes: `go vet ./... && go test ./...`, then `scripts/build-cli.sh` to cross-build.
- CLI releases: push a tag `v*` (e.g. `v1.0.1`) — CI tests, builds all three hosts, publishes the release.
- Package additions: dispatch the matching `build-*.yml` workflow with the desired version; releases and catalog.json update automatically.
- Bionic build issues are fixed at the builder level (see `builder/*/patches`), not by patching output archives.

## Status / verification

- CLI: `go test ./cmd/apex` covers catalog parsing, package resolution, manifest handling.
- E2E on-device (Android/Termux arm64): `apex --list`, `licenses --accept`, `install platform-tools;37.0.1`, `platforms;android-34`, `build-tools;33.0.0`, `cmake;3.31.6`, `ndk;27.3.13750724`; verified `aapt2 version`, `cmake --version`, native compile with the packaged NDK clang.
